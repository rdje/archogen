# The S0 early generation path

Most of this book describes the supported path: describe a system, check it, resolve it, build
it, and read a report that says what was established. **S0** is a deliberate shortcut through
all of that, taken early and on purpose.

Its question is not "does the toolchain work?" but "is the *shape* of the pipeline right,
before the foundation becomes expensive to change?" So it takes a sixteen-line description
through one fixed engine-owned realization to a running hosted executable, and it makes no
claim beyond what that executable printed.

> **The output is experimental.** S0 establishes no catalog reuse, no scheduling result, and
> nothing about real hardware. `ROADMAP.md` §12 S0 is explicit: its value is "discovering
> pipeline mistakes before the foundation becomes expensive to change".

## The gate: the oracle comes first

F28's interesting clause is not about the executable. It is about the order things were written
in:

> Before generating, write an independent expected-output assertion for this limited behavior.
> […] Changing only a comment or embedding a prebuilt output without consuming the functional
> input does not satisfy the gate.

An expected output written after the generator is not an expectation — it is a transcript. So
the three descriptions and their frozen observations landed in leaf `S0.1`, and the emitter in
`S0.3`, two commits later. The independence claim is therefore a fact of the commit history
rather than an assertion anyone has to trust — and when the emitter was finished, both runnable
fixtures produced output **byte-identical** to what had been frozen before it existed.

Two further things keep it that way:

- The oracle lives in `crates/archogen-cli/tests/s0_oracle.rs`. Rust cannot link an integration
  test into a library, so **no future emitter can call it** — the emitter has to be written from
  the contract below rather than from the code that judges it.
- The oracle discloses what it *does* share with the toolchain: the eADL reader, and nothing
  else. §4.4 asks for shared logic to be named, not eliminated.

## The corpus

Three descriptions in `examples/s0-heartbeat/`, each one the base plus exactly one functional
change:

| Case | The change | `archogen check` | `archogen build` |
| --- | --- | --- | --- |
| base | — | `0` | `0` — 4 releases over a 30 ms hyperperiod |
| changed | `chime` released every 20 ms instead of 30 ms | `0` | `0` — 3 releases over a 20 ms hyperperiod |
| unsupported | `chime` becomes sporadic | `0` | `12` `unsupported-profile` |

The third row is the one worth pausing on. It is **accepted** by `archogen check`: §3.1 admits
"periodic or sporadic releases with declared minimum separation", so a sporadic task is valid
eADL inside the supported profile. What has no realization is the *engine* — S0 derives its
observation from declared periods, and a minimum separation says how close two releases may be,
never when one happens.

So the refusal arrives from generation, and §5.4 fixes its wording: *"If no known realization
exists, explain the missing engine capability; do not declare the requested function logically
impossible."* The diagnostic names the missing capability — a modeled event source — and the
leaf that will supply it.

That distinction is the difference between "this toolchain cannot do that yet" and "that is not
a sensible thing to ask for", and a toolchain that blurs it teaches its users to stop asking.

## The observation contract

What a generated S0 system does is the engine's decision. The description says nothing about
message text or run length — writing either one into eADL would be the "prebuilt output" F28
rules out. The rules:

1. **Horizon.** Modeled time runs from `0` to the hyperperiod `H` — the least common multiple
   of the declared task periods. That is the repeating unit of a periodic release schedule, so
   it is the shortest horizon that shows the whole behavior, and it is a function of the
   description rather than a knob.
2. **Releases.** A task of period `T` is released at every `t = k·T` with `0 ≤ t < H`.
3. **Order.** Ascending time; coincident releases by ascending priority rank, because a
   numerically lower priority is a higher one.
4. **Form.** A `system` line, one `release` line per release, and a closing `summary` line.
5. **Refusal.** A task with a minimum separation and no period has no derivable schedule.

For the base description — `beat` every 10 ms, `chime` every 30 ms — that gives
`H = lcm(10, 30) = 30 ms`, releases of `beat` at 0, 10 and 20, one release of `chime` at 0, and:

```text
system heartbeat
release 0 ms beat
release 0 ms chime
release 10 ms beat
release 20 ms beat
summary hyperperiod 30 ms releases 4
```

Move `chime` to a 20 ms period and the horizon shortens to 20 ms, the 20 ms `beat` release falls
outside it, and the count drops to 3. One changed number moves the horizon, the count and the
trace together — which is what makes it a test of whether the functional input was consumed.

⛔ **These are release events, not an execution trace.** A release follows from the description;
when a task actually runs is a scheduling result, and S0 establishes none.

## Building one

```console
$ archogen build examples/s0-heartbeat/system.eadl --out build/heartbeat
examples/s0-heartbeat/system.eadl: generated `heartbeat` into build/heartbeat
  4 file(s): Cargo.toml, src/main.rs, src/rt.rs, src/service.rs
  2 task(s), hyperperiod 30 ms
  experimental: this is the S0 path — one fixed realization, periodic releases, the hosted playground.
    It is not a complete system and carries no timing or assurance claim. See `archogen help build`.
  next: cargo run --manifest-path build/heartbeat/Cargo.toml

$ cargo run --quiet --manifest-path build/heartbeat/Cargo.toml
system heartbeat
release 0 ms beat
release 0 ms chime
release 10 ms beat
release 20 ms beat
summary hyperperiod 30 ms releases 4
```

Four files, and only one of them is generated in any interesting sense:

| File | What it is |
| --- | --- |
| `Cargo.toml` | a manifest, with `[workspace]` so the crate builds wherever it is written |
| `src/main.rs` | **the only specialized file**: the plan as a table, and the call that runs it |
| `src/rt.rs` | engine-owned, copied verbatim — the modeled-time release loop |
| `src/service.rs` | engine-owned, copied verbatim — `console.write` on the hosted playground |

⭐ The last two are not string templates. They are ordinary modules of `crates/archogen-s0`,
compiled, linted and unit-tested there, and read into the output with `include_str!` — with a
test asserting the emitted bytes equal the reviewed source. A template held as a string is Rust
that nothing type-checks until a user compiles the output, and §12 S0 requires "all templates,
service code, and dispatch choices" to stay inside the engine. This is what that costs and what
it buys: generation emits a **table**, never behavior.

Every generated file says, in its own header, that it is generated, that editing it is pointless,
and that it is experimental. So does the command, and so does `archogen --help`.

## `--locked` is refused, not ignored

```console
$ archogen build examples/s0-heartbeat/system.eadl --out build/x --locked
archogen: unimplemented: `--locked` is not implemented on the experimental S0 build path
  hint: the S0 path emits no lock data, so there is nothing to check a locked build against —
        and a build that accepted the flag silently would be an unlocked build wearing a locked
        build's label. Lock data is ROADMAP.md §10.3 and task-tree leaf M4.1.
$ echo $?
20
```

The flag's contract is "fail on any missing or mismatched locked input". The S0 path emits no
lock data, so it cannot honor that — and accepting the flag would hand someone who asked for a
reproducible build an ordinary one that claimed to be reproducible. Refusing costs a user one
re-run; accepting costs them a belief.

What the S0 path *can* say about reproducibility, it says and tests: generation is deterministic,
so two builds of one description from clean directories produce identical bytes.

## When the description is broken

F28 asks for more than a working case: *"failure points have useful diagnostics and basic source
provenance."* The first half of that is already true of the frontend, and the S0 corpus asserts
it rather than assuming it — corrupt the base description and the refusal has to say **where**:

```console
$ archogen check build/s0/malformed.eadl
error[read-unclosed-list]: this list is never closed
  --> build/s0/malformed.eadl:41:1
   |
41 | 
   | ^ input ends here, still inside a list
  --> build/s0/malformed.eadl:32:1
   |
32 | (defsystem heartbeat
   | - opened here
  = hint: add the matching `)`
archogen: invalid-description: 1 diagnostic(s) in build/s0/malformed.eadl
$ echo $?
10
```

The second label is the useful one. A reader that only said "unexpected end of file" would leave
the author searching the whole description by hand, and it would pass any test that merely
checked an error was produced. So the assertion is about *position*: a stray `)` injected near
the top of the file must be reported on that line, not at the end — and the expected line is
computed from the fixture, so moving a declaration moves the expectation with it.

That the test can fail was measured, not assumed: rewriting the reader's label to point at
offset zero turns it red, and the reader was restored afterwards.

## What S0 owes the supported path

S0 is allowed to hard-code, and is not allowed to keep it quiet. Every temporary assumption is
listed with the leaf that removes it, so that — in the roadmap's words — "no hidden special-case
generator is grandfathered into the release":

| Assumption | Retired by |
| --- | --- |
| the horizon is exactly one hyperperiod | `M4.3` |
| task periods must be whole milliseconds | `M4.1` |
| the event format is fixed and engine-internal | `M4.3` |
| only periodic releases are realized | `M4.3` |
| one fixed realization, no provider search | `M3` |
