# The S0 early generation path

## The idea, in plain words

Before a house is built properly, an architect may make a cardboard model, to see whether the rooms connect the way
they were meant to. **S0** was archogen's cardboard model: a small path, taken early and on purpose, that turned a
tiny description — two tasks, one released every 10 ms and one every 30 — into a program that ran on your computer
and printed when each task was released. Mistakes in the *shape* of the pipeline showed up while they were still cheap
to fix.

⭐ **It has done its job.** `archogen build` no longer goes this way: it goes through the checked runtime plan ([Building a
system](building.md)), and the prototype is deleted. What outlives it is what this chapter is now about: the fixtures, the rule
that an expected output is written before the code it judges, and what a green gate turned out not to see.

> **In one minute, for engineers.** `ROADMAP.md` §12's S0, gated by F28: one engine-owned realization from a
> periodic workload to a hosted Rust executable that printed its releases over the hyperperiod. Each case's frozen
> observation landed before the emitter, so the oracle's independence is a fact of the commit history, and the same bytes
> now judge the supported path (`crates/archogen-cli/tests/functional_fixtures.rs`). What became of each of the path's temporary
> assumptions is `docs/decisions/decision_s0-retirement.md`. `crates/archogen-cli/tests/s0_chapter.rs` holds this chapter's corpus
> table to the directory.

## How it works

Most of this book describes the supported path: describe a system, check it, resolve it, build
it, and read a report that says what was established. **S0** was a deliberate shortcut through
all of that, taken early and on purpose.

Its question was not "does the toolchain work?" but "is the *shape* of the pipeline right,
before the foundation becomes expensive to change?" So it took a sixteen-line description
through one fixed engine-owned realization to a running hosted executable, and it made no
claim beyond what that executable printed.

### The gate: the oracle comes first

F28's interesting clause is not about the executable. It is about the order things were written
in:

> Before generating, write an independent expected-output assertion for this limited behavior.
> […] Changing only a comment or embedding a prebuilt output without consuming the functional
> input does not satisfy the gate.

An expected output written after the generator is not an expectation — it is a transcript. So
the three descriptions and their frozen observations landed in leaf `S0.1`, and the emitter in
`S0.3`, two commits later. The independence claim is therefore a fact of the commit history
rather than an assertion anyone has to trust — and when the emitter was finished, both runnable
fixtures produced output **byte-identical** to what had been frozen before it existed.

Two further things keep it that way:

- The oracle lives in `crates/archogen-cli/tests/functional_fixtures.rs`. Rust cannot link an integration
  test into a library, so **no emitter can call it** — an emitter has to be written from
  the contract below rather than from the code that judges it. Today's was, and it passed.
- The oracle discloses what it *does* share with the toolchain: the eADL reader, and nothing
  else. §4.4 asks for shared logic to be named, not eliminated.

### The corpus

Four descriptions in `examples/s0-heartbeat/`, each one the base plus exactly one functional
change:

| Case | The change | `archogen check` | `archogen build` |
| --- | --- | --- | --- |
| base | — | `0` | `0` — 4 releases over a 30 ms hyperperiod |
| changed | `chime` released every 20 ms instead of 30 ms | `0` | `0` — 3 releases over a 20 ms hyperperiod |
| unsupported | `chime` becomes sporadic | `0` | `11` `missing-fact` |
| non-harmonic | `chime` released every 15 ms instead of 30 ms | `0` | `0` — 5 releases over a 30 ms hyperperiod |

The third row is the one worth pausing on. It is **accepted** by `archogen check`: §3.1 admits
"periodic or sporadic releases with declared minimum separation", so a sporadic task is valid
eADL inside the supported profile. What generation lacks is a fact: nothing in the description says
what releases `chime`, and a minimum separation says how close two releases may be, never when one
happens.

S0 could only call that `unsupported-profile`, naming a modeled event source as the capability it did
not have, because §5.4 asks that a missing capability be explained rather than the request declared
impossible. The supported path has event sources, so the frozen answer moved, with its reason in its
own header: `missing-fact`, repaired by the task's own `(needs interrupt-source)`.

The last row came later, from a mutation rather than from the design (leaf `S0.4`). In the base and
changed cases one period divides the other, so the hyperperiod is also the longest period, and a
realization that computed the maximum instead of the least common multiple passed every case. `chime`
every 15 ms against `beat`'s 10 ms breaks that: the hyperperiod is 30 ms and the longest period is 15,
so only the right computation observes five releases. The count at the top of this section and every
row of this table are compared with the directory by `crates/archogen-cli/tests/s0_chapter.rs` (leaf
`S0.8`), because the count once stayed at three from `699a068`, where this row's description arrived, until the
commit that added that test.

The distinction between "this toolchain cannot do that yet" and "that is not a sensible thing to ask
for" is why either answer names its repair: a toolchain that blurs them teaches its users to stop asking.

### The observation contract

What a generated system is observed to do is the engine's decision. The description says nothing about
message text or run length — writing either one into eADL would be the "prebuilt output" F28
rules out. The rules, in the form the frozen files write them, which the test reads out of today's trace:

1. **Horizon.** Modeled time runs from `0` to the hyperperiod `H` — the least common multiple
   of the declared task periods. That is the repeating unit of a periodic release schedule, so
   it is the shortest horizon that shows the whole behavior, and it is a function of the
   description rather than a knob.
2. **Releases.** A task of period `T` is released at every `t = k·T` with `0 ≤ t < H`.
3. **Order.** Ascending time; coincident releases by ascending priority rank, because a
   numerically lower priority is a higher one.
4. **Form.** A `system` line, one `release` line per release, and a closing `summary` line.
5. **Refusal.** A task with a minimum separation and nothing to release it has no derivable schedule.

For the base description — `beat` every 10 ms, `chime` every 30 ms — that gives
`H = lcm(10, 30) = 30 ms`, releases of `beat` at 0, 10 and 20, one release of `chime` at 0, and:

```text
system heartbeat
release 0 ms beat
release 0 ms chime
release 10 ms beat
release 20 ms beat
summary hyperperiod 30 ms releases 4
```

Move `chime` to a 20 ms period and the horizon shortens to 20 ms, the 20 ms `beat` release falls
outside it, and the count drops to 3. One changed number moves the horizon, the count and the
trace together — which is what makes it a test of whether the functional input was consumed.

⛔ **These are release events, not an execution trace.** A release follows from the description;
when a task actually runs is a scheduling result, which no trace of an empty job establishes.

### What it wrote, and where that went

S0 wrote five files: a manifest, a `main` holding the plan as a table, two engine-owned modules copied verbatim, and a
`provenance.json`. Three of its ideas moved into the supported path, unchanged in spirit ([Building a system](building.md)):
generation writes a table and never behavior; `--locked` is refused rather than ignored until lock data exists; and every
provenance entry is resolved from both ends by a test, since the failure to fear is an entry pointing somewhere wrong.

### When the description is broken

F28 asks for more than a working case: *"failure points have useful diagnostics and basic source
provenance."* The first half of that is already true of the frontend, and the S0 corpus asserts
it rather than assuming it — corrupt the base description and the refusal has to say **where**:

What follows is one row of `docs/semantics/reference.md` §4, which states every code the reader can
emit, when it fires, and what to do about it. The `hint:` line at the end is that requirement rather
than a courtesy: §5.5 makes a repair direction part of the user contract, and §4 rule 1 makes every
one of them an error, so a refusal that only said "no" would be a breach of both.

```console
$ archogen check build/s0/malformed.eadl
error[read-unclosed-list]: this list is never closed
  --> build/s0/malformed.eadl:42:36
   |
42 |   (platform (uses host.playground))
   |                                    ^ input ends here, still inside a list
  --> build/s0/malformed.eadl:34:1
   |
34 | (defsystem heartbeat
   | - opened here
  = hint: add the matching `)`
archogen: invalid-description: 1 diagnostic(s) in build/s0/malformed.eadl
$ echo $?
10
```

The second label is the useful one. A reader that only said "unexpected end of file" would leave
the author searching the whole description by hand, and it would pass any test that merely
checked an error was produced. So the assertion is about *position*: a stray `)` injected near
the top of the file must be reported on that line, not at the end — and the expected line is
computed from the fixture, so moving a declaration moves the expectation with it.

That the test can fail was measured, not assumed: rewriting the reader's label to point at
offset zero turns it red, and the reader was restored afterwards.

### F28, and what it could not see

The gate runs as an automated test. For each runnable case it removes the build directory,
generates, compiles, runs the produced executable, and compares what it observes to the frozen
bytes — plus the unsupported case's refusal, plus a repeat pass proving that deleting the build
directory changes nothing, plus a check that no generated file differed between generation and
execution. F28's "without editing generated output" is therefore a fact about the run rather than
an assurance about the author.

It was green. It was also blind.

⛔ **Replacing the hyperperiod with the longest period left every test passing.** Both fixtures
are *harmonic* — 10 against 30, then 10 against 20 — so one period divides the other and
`lcm` equals `max` on every input the corpus had. The fixtures were not wrong: they were picked to
be checkable by hand, which is the same property that collapses the two formulas onto one answer.

It was found only because the gate was mutation-tested rather than trusted, and it was closed at
both levels — a unit test where `lcm(10, 15) = 30` against a longest period of `15`, and a fourth
description, `system-non-harmonic.eadl`, that runs the whole path on non-dividing periods, as it
still does on the supported path.

The generalisation is worth more than the bug. A fixture set can be complete against its own
specification and blind to a class of error, and a green gate says nothing about which. The
programme's acceptance matrix is thirty such fixtures, described in the roadmap as "a minimum
practical corpus, not a proof of completeness" — this is the first measured instance of what that
sentence costs.

⚠️ One asymmetry is preserved deliberately: the fourth description has **no frozen expectation**.
The three original ones predate the emitter, which is the whole basis of the independence claim;
a file frozen afterwards would sit beside them with a weaker pedigree nobody could later tell
apart. Its expected observation is derived by the oracle instead — two independent
implementations agreeing, which is weaker evidence than a literal frozen in advance, and the
right strength for a case added afterwards.

## What became of it

### What S0 owed the supported path

S0 was allowed to hard-code, and was not allowed to keep it quiet, so that, in the roadmap's words, "no hidden special-case
generator is grandfathered into the release". Each temporary assumption was marked at the line that made it and listed with the
leaf that removed it, and a doctrine checked on every commit that each marker was listed, each listed leaf existed, and the crate
had acquired no consumer beyond its own tests. The prototype that kept to that bargain is gone:

| Assumption | What became of it |
| --- | --- |
| the horizon is exactly one hyperperiod | a named rule of a run, and `M4.3` may add others |
| task periods must be whole milliseconds | gone: exact ticks, down to what the durations the run repeats need |
| only periodic releases are realized | gone: the simulator's sources arrive and release their tasks |
| the observation format is fixed and engine-internal | gone: the trace is a registered format |
| standard output realizes `observable-output`, with no device model | still so, `M4.3`'s: no job writes anything yet |
| one fixed realization, no candidate enumeration or provider search | gone: the search |
| the plan is never independently re-checked against the description | gone: the configuration checker |
| the provenance `realization` is a stub of a §9 catalog entry | gone: the build's provenance holds no such member |
| no assurance report, so the build makes no claim of any kind | still so, `M4.8`'s, and the build says so |
| no lock data, so `--locked` is refused | still so, `M4.7`'s, and the supported path's own refusal |

⭐ **The third leg was the one that caught what grandfathering really looks like**: nobody *decides* to keep a prototype, it just
stops being noticed. So the crate could gain no consumer by accident. ⚠️ And an honest limit, stated in the check itself: none of
it forced anyone to *write* a marker for something new. It made an unmarked assumption a thing someone chose not to record, rather
than a thing nobody noticed.

#### What survives

The four descriptions survive — they are feature-only, and outlive any realization. The frozen observations have outlived the
realization they were first compared with: a change to one must say why in its own header, never quietly edit it. The realization
itself did not survive. Deleting it was the retirement.
