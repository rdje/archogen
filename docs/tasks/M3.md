# M3: joint realization search and independently checked plan

## Metadata

- Tree ID: `M3`
- Status: `active` — since `2026-10-03`, `M2`'s open leaves all waiting on the director
- Roadmap lane: `ROADMAP.md` §12 M3; §5.4; §4.4; §14.4; §18 work package 10; fixtures F08–F12, F30
- Created: `2026-09-13`
- Owner: repo-local workflow

## Goal

Turn a typed description into a complete, deterministic, independently checked build plan:
direct feature matching plus realization through engine rules, joint constraint solving over
capacity, ownership, topology, privilege, placement and initialization order, and a separate
checker that re-evaluates the original requirements against the whole returned assignment.

## Non-Goals

- No optimization or optimality claim (§5.4: feasibility before optimization).
- No SAT/SMT dependency without a measured need and a recorded trust-boundary role.
- No code emission. That is `M4`.

## Acceptance Criteria (roadmap exit gate, §12 M3)

- The positive corpus produces checked plans.
- Resource oversubscription, ownership conflicts, stale assumptions, illegal placements, and
  incompatible provider combinations are rejected with explanations.
- The same locked input resolves deterministically.
- F30 shows that unreviewed generator/checker sharing, or a relevant feature/source change,
  is mechanically surfaced and blocks acceptance.
- No optimality claim is made unless separately established.

  (`M3.6.9.6.3.2.2.15.2.1.6.1.1.2`): a refusal is the inventory's judgment of a record it read, and a record
  Cargo refused was never read, so no input can be named without reading past the producer's own refusal;
  the gate fails on the error, nothing is written, and the outcome is unjudged, not passed. The reader's own
  refusal of such a record stands behind Cargo's, so the inventory does not rest on Cargo's message.
