# S0: early executable generation path

## Metadata

- Tree ID: `S0`
- Status: `active`
- Roadmap lane: `ROADMAP.md` §12 S0; §18 work package 3; fixture F28
- Created: `2026-09-13`
- Owner: repo-local workflow

## Goal

Prove the shape of the whole pipeline before the foundation is expensive to change: take a
roughly twenty-line feature-only description, interpret it minimally, select one fixed
engine-owned implementation, emit Rust, compile it, run it, and observe an independently
asserted result — with a changed-input case and a rejected unsupported case.

## Non-Goals

- No catalog reuse, no sound scheduling, no real-time assurance, no claim of OS
  completeness. The output is marked experimental.
- No universal matcher, no complete schemas, no physical board.

## Acceptance Criteria (roadmap exit gate F28, §12 S0)

- From a clean local build directory, the small description produces an executable and the
  asserted observation, with no edits to generated output.
- The changed-description case produces the corresponding changed observation.
- The unsupported request is rejected with a diagnostic.
- Failure points carry useful diagnostics and basic source provenance.
- The expected-output assertion was written before generation, independently of the emitter.

  ### Scope decision, recorded because it was a judgement call

  Making `build` real forced a third state onto the command surface. `CommandSpec` carried
  `owner: Option<&str>` — built, or unimplemented — and neither fits a command that runs over a
  deliberately narrow path. Marking it **built** promises the §10.2 command ("a complete system
  and its simulator"); marking it **unimplemented** denies a command that works. §12 S0 settles
  it by requiring the output to be marked experimental, so `Maturity` has three variants and the
  help text renders all three. The cost is a small refactor of `spec.rs` and `cli.rs`; the
  alternative was a help text that lies in one direction or the other.

  ### Decision recorded because it weakens a claim if taken silently

  `system-non-harmonic.eadl` has **no frozen expectation**. The three F28 cases were frozen before
  any emitter existed, and that ordering is the whole basis of §12 S0's independence claim. A
  fourth file frozen afterwards would sit beside them carrying a materially weaker pedigree that
  no later reader could tell apart — and the likeliest outcome is that the weaker one gets
  credited with the stronger claim. So its expectation is *derived* by the oracle, whose
  implementation predates the emitter and which the emitter cannot call, and compared against what
  the generated system prints. Two independent implementations agreeing is weaker evidence than a
  literal frozen in advance; it is the right strength for a case added afterwards, and it is
  labelled as such in the file, the README and the test.

## Decisions

- `2026-09-13`: the oracle is written and committed in `S0.1`, strictly before `S0.3`, so the
  independence claim in §12 S0 is a fact of the commit order, not an assertion.
- `2026-09-13`: the oracle lives in `crates/archogen-cli/tests/`, and that placement is the
  independence mechanism rather than a filing choice — Rust cannot link an integration test into
  a library, so no emitter can ever call the derivation that judges it.
- `2026-09-13`: **the observation horizon is the hyperperiod**, not a declared run length. A run
  length in the description would be the engine's observation policy smuggled into eADL, and a
  run length in the engine would be arbitrary; the least common multiple of the declared periods
  is the repeating unit of the schedule, so it is both a function of the description and the
  shortest horizon that shows the whole behavior.
- `2026-09-13`: the S0 fixture declares **two** tasks. With one, the hyperperiod is one period
  and the trace is one event, so no parameter change can produce a different observation and the
  changed-input half of F28 would be untestable.
- `2026-09-13`: the unsupported case is a **realization** gap, not a profile violation. §3.1
  admits sporadic releases, so `archogen check` accepts it and generation refuses it — which
  tests S0's own path and gives F10's shape ("missing engine support, not universal
  impossibility") early. A profile-excluded fixture would have re-tested M1.
- `2026-09-13`: the S0 realization lives in `crates/archogen-s0`, **not** in `archogen-plan` or
  `archogen-emit`. Those are the §4.2 names `M4` builds under; a prototype holding them stops
  looking like a prototype, which is exactly how §12 S0's "no hidden special-case generator is
  grandfathered" gets violated. Retiring S0 is then one visible operation: delete the crate.
- `2026-09-13`: the engine-owned runtime is a **module of the engine**, read with `include_str!`,
  not a string literal. A template held as a string is Rust that nothing type-checks until a user
  compiles the output; held as a module it is compiled, linted and tested here, and a test
  asserts the emitted bytes equal the reviewed source.
- `2026-09-13`: `--locked` is **refused** on the S0 path rather than accepted and ignored. The
  path emits no lock data, so honoring the flag is impossible and appearing to honor it is worse:
  the user would get an ordinary build wearing a locked build's label.
- `2026-09-13`: the command surface gained a third maturity state, `Experimental`. §12 S0
  requires the output to be marked experimental, and a built/unbuilt flag cannot express a
  command that runs over a narrow path without lying in one direction.
- `2026-09-13`: a numerically lower `priority` is a higher priority
  (`docs/decisions/decision_priority-comparison-direction.md`). Discovered here: the direction
  was needed to order two coincident releases and was nowhere recorded.
