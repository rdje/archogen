# M2: one complete engine realization and its controls

## Metadata

- Tree ID: `M2`
- Status: `active`
- Roadmap lane: `ROADMAP.md` §12 M2; §7; §8; §9; §18 work packages 7, 8, 9; fixtures F17, F18, F29
- Created: `2026-09-13`
- Owner: repo-local workflow

## Goal

Build one end-to-end engine catalog slice — fixed-priority scheduling behavior, task
lifecycle, timer management, interrupt dispatch, static allocation and layout — together with
the independent controls that make its claims meaningful: a separate reference model, a
scheduling checker with explicit applicability conditions, the cost-accounting contract, and
the first trust-dependency inventory.

## Non-Goals

- No joint resolver (that is `M3`) and no complete generated system (that is `M4`).
- The architecture spike is a falsification control; it must not become a second production
  kernel or dictate eADL's feature categories.
- No timing claim for any board merely because the checker works on abstract fixtures.

## Acceptance Criteria (roadmap exit gate, §12 M2)

- One catalog slice carries functional requirements, internal contracts, implementation,
  an independent reference, analysis applicability, and tests.
- Deliberate scheduler and timer errors are detected.
- The target spike has produced evidence or a named blocker.
- F18, F29 and the F17 refusal behavior pass.

  ### Two decisions that shape what the analysis can say

  **The oracle is parsed out of `ROADMAP.md` §13.2 rather than copied into the test.** §14.1
  forbids implementation changes that "silently … adjust expected oracle results", and a test
  carrying its own copy of the numbers makes exactly that a one-line edit that looks like a fix.
  Reading the published table makes the expectation and the requirement the same object. The
  parser asserts the row count, because a table that quietly shrank would leave a green test
  checking less than it did.

  **The iteration runs to its fixed point, bounded by `T`, not stopped at `D`.** Stopping as soon
  as an iterate exceeds the deadline is sound for a yes/no answer and destroys the witness: §13.2
  asks the deadline-3 variant for "a concrete deadline-violation witness", and the useful witness
  is the converged response `4`, not the first iterate above `3`. So convergence and the deadline
  comparison are separate steps, and non-convergence stays `analysis-inconclusive` — §7.4 is
  explicit that a conservative failure is not a counterexample.

  ### Why the rule is a type and not a checklist

  The failure §7.4.1 describes has a specific shape: **the wrong answer looks exactly like the
  right one.** A ledger that charges an interrupt twice still totals a plausible number, and
  nothing about it invites suspicion — so a check that depends on suspicion never fires. That is
  the third time this project has answered such a rule with a constructor precondition rather
  than a review step (`Conclusion` for §7.1, `TaskSet::admit` for §7.4, `Ledger::seal` here), and
  the pattern is now recorded in `docs/knowledge/make-the-rule-a-constructor-precondition.md`.
