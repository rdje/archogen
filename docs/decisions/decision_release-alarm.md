# The release alarm: which device releases tasks on a target, and what a timer route costs

- **Type:** `decision`
- **Date:** `2026-11-06`
- **Status:** `active` — written by leaf `M4.1.6`; nothing here is yet code but the executable model that holds its claims, `crates/rt-analysis/tests/alarm_model.rs`, and reviewed in `docs/reviews/decision_release-alarm-reviews.md`, closed on round 16, which found no defect
- **External sources:** [the privileged specification](../book/src/ledger.md#riscv-privileged), for what its machine timer's compare reads (§2's `window`); otherwise none: this record decides how the engine reads its own records
- **Owner / source:** leaf `M4.1.6` (`docs/tasks/M4.md`), filed by `M4.1.1`'s round-3 answer and widened by `M2.30`'s review (R10); `ROADMAP.md` §6.2, §7.3 and §7.4; the kept question R3-1 of `docs/reviews/decision_runtime-plan-reviews.md`, and rounds 21 and 26 there.

## The fact / decision

**In plain words.** On the playground the simulator's clock releases tasks, so no device is involved. On a real machine something must raise the interrupt that releases them, and that something is a device like any other. So the kernel becomes one more requester of the system: it asks for an alarm, and the search binds it to a device that can serve, under the same rules and the same count of channels as anything else that asks. A second alarm, an adapter's say, takes a channel of its own, on another device than the kernel's, since the two reach the core differently. Each such alarm's interrupt is charged as any other interrupt source is, since the analysis was proved for sources and says so of timekeeping interrupts by name. What it must be told is how close two arrivals can come, and no job's choice of deadlines is left to decide that: the code programming an alarm holds its compare a least distance past the last arrival, so the figure is true whatever a job does. And a job never runs inside an interrupt, so a job hears of an alarm when a task is released.

### 1. The release timer is a requester

Where a system runs on a target, and has a task whose trigger is `timer`, the engine adds one requester, the **release requester**, named by the system, with these requirements:

```text
(needs relative-delay counter-modulus tick-rate observation-coherent)
(available-in-state idle)
(alarm-wiring core)
(alarm-kind level-compare)
(unambiguous-horizon (at-least SHORTEST))
(supported-horizon (at-least SHORTEST))
```

- **`SHORTEST`** is the shortest `period` of a timer-released task, rounded up to a tick wherever it enters a sum of lags, where the variant rounds a separation down. The analysis's condition 6 takes a timer interrupt "only when a release is due", so no trap may fall between two releases to re-arm it, and one compare must reach from a release to the next. The next due release is at most the shortest period away, whichever task it is, since every timer task is released from time zero at its own nominal releases. A long period does not ask more: the service runs at the shortest, and counts wraps there.
- **That is necessary, not sufficient.** A compare over a modular counter cannot tell a value it has passed from one a whole wrap ahead, so with `λ` the most from a due-check to the compare's write landing, `SHORTEST + λ` must lie within the horizon, and `λ` within its device's `compare-window` (§2's `window`): `a_modular_counter_tells_a_deadline_past_from_one_ahead_only_within_its_modulus` holds that, over each modulus, reach and lag it tries, as exactly the condition. `λ` is bounded by `J^release + C_rel`, which only the analysis knows, so the scheduling checker holds it (`RA-H2`). A device that passes the search and fails there is refused there, naming that.
- **And one write must reach that far.** The horizon says how far a counter can be told apart, and `H`, what one write reaches, how far one compare can be set, and a device can have the one without the other. A release's next compare stands at most `SHORTEST + 2ρ` past its read: the next release is at most `SHORTEST` past the last, a read is at most `ρ` behind the time, and the value rounds up by `ρ`. The first stands no farther: time zero is the port's read plus the bound on its transition, at or after the first enabling, and that bound lies within `S`, so within `L`, and so under `SHORTEST`, once the analysis admits the set (`RA-H8`, `decision_runtime-plan-format-2.md` §4). The search asks `H` and cannot know `ρ`, so the scheduling checker holds this too (`RA-H2`).
- **`available-in-state idle`.** The idle context waits for the next interrupt, so a timer that stops in idle loses every release after it (`ROADMAP.md` §6.2's "clock-state dependencies").
- **`alarm-wiring`** is a fact this record adds: how a device's alarm reaches the core, `core`, a hart-local timer line a trap takes with no claim, or `controller`, a request at the interrupt controller that a claim takes. Condition 5 asks exactly this of the two: "a timer trap the timer's, claiming nothing", and any other trap's one claim. One block states one wiring, so a machine with both describes two blocks. Without this fact a second channel repairs nothing where the wiring is uniform, and the search's first pick could give the release timer the device an alarm needs.
- **It takes a channel** (model §8 rules 2 and 3), and so the release timer and an alarm are on two blocks by their wiring, whatever each one's channels. What does share a device, two alarms on one wired to the controller, is judged with no new rule. There `channels` counts lines to the controller, so a device of two comparators on one line states `channels 1`, and a second alarm's repair is another device; where rule 14 binds the two to one device there is none, and the refusal is all there is.
- **Which device** is what the search binds, by the policy's order and then its stable one. So it is never "the target's tick-rate block", R3-1's rejected fix: a counter may raise no interrupt, and `relative-delay` is what says this one can.
- **What the joint rules need said.** Rule 1 gains this requester, rules 7 and 12 name it among what a system serves, rule 8 gives no route for its binding, since the release timer is no route, and rule 9 reads it as a caller at the system's level. Those lines land with the code (`RA-H1`), as do the assignment's format and the checker's own reading of it (`DC-H2`). The record supplying `C_rel` states the device its code programs (`RA-H5`), and the analysis reads the compare's facts of that device, `H` and `compare-window` or `compare-magnitude` among them, and that record's `ρ`.
- **On the playground there is no release requester.** The release timer stays the simulator's exact clock, written `simulator` (the runtime plan's §2.5, `RTP-H9`). Nothing in `/1` moves.
- **With no timer-released task on a target** there is no release requester and no device: `/2` writes `(timer none)`, and the timer's interrupt is never enabled. "Bound and never due" does not hold of a modular compare, whose largest value comes round within a wrap, and a trap finding no release due is an unexpected trap (the fault contract). So the variant owes this case its own reading, since it now declares a timer of every set: no `C_rel`, `ρ` or condition 6's facts are asked, and the timer term is zero, which it is, no task being released by it (`RA-H2`).
- **What a target must state:** those facts, `compare-step`, `compare-window` or `compare-magnitude`, and `channels`, each with what checks it, which is `DC-H1`'s obligation: the agreement gains a rule for each, and a fact it cannot read off its source stays unstated, so a system asking it is refused `missing-fact` until a source says. A statement's evidence is its agreement's, and a §7.3 record is the realization's, for what is a cost. It asks a level compare, since the variant's condition 6 rests on one and would refuse any other after a binding. The joint rules ask the release requester's device for `compare-step` and one of those two as they ask an alarm's, and refuse `missing-fact` there too (`RA-H1`), so what the scheduling checker reads as owed is only what a plan's line lacks.
- **`H` is a fact the vocabulary has.** What one write reaches is the relation's programming range, `supported-horizon`, "a capacity". A device stating no value of it has no `H`: silence is no offer, and a counter's horizon says how far it can be told apart and not how far a compare reaches. So the search refuses `missing-fact`, and for an alarm the joint rules do (`RA-H1`). A target states at most what its source says, which is all a capacity needs and may be all it can write: 2^64 ticks at 10 MHz is no number the language reads (`RA-H8`).
- **So is what `ρ` reads.** An alarm's `ρ` is one step of `compare-step`, a fact this record adds, how far apart two values its compare can match or two counts its delay can, a count of its counter's ticks, which `tick-rate` makes a time. One finer is refused (`RA-H8`), since values then lie off the grid its reads lie on: a delay counting 1 on a read of 16 put arrivals 3 apart under a floor of 40, and left a deadline pending 7,919 against a `delivery` of 79. `tick-rate` cannot say it, since a compare can match coarser than its counter counts, and what the agreement compares with the device tree cannot be restated: on a step of 16 and a tick of 1, code told only the tick puts arrivals 16 apart under a floor of 31. It is the whole step, as the release timer's figure is below: rounding adds less than a step to an instant, and an alarm's also says how far a read lies behind a time, each falling anywhere. On a step of one unit and a floor of 20, a landing at 100.9 reads back as 100: a figure less than the step is nothing there, so the bound would be 100 and the next arrival 120, 19.1 after it.
  The generated code rounds to that step and no coarser (`RA-H6`), which is the resolution the model runs. So no record states either for an alarm, which has none (the catalog's §12 holds one `compare-rounding` to a target, the timer service's, and generated code is in no record), and one figure has one statement. The release timer's `ρ` stays the variant's, that record's `compare-rounding`, the catalog's worst case over all release instants. A period is an exact duration, so a release falls anywhere, and rounding up adds any figure short of a whole step: 667 ns at 1 MHz on a period of 1/3 ms. So the worst case rounded up to the analysis's unit is one step rounded up, 42 ns at 24 MHz on a unit of 1 ns and 16 units on a step of 16, and the composition holds the figure at least that (`RA-H5`). One below it is evidence that cannot be true, `analysis-inconclusive` as the variant's §5 reads a declared delay below its floor, this floor being `RA-H5`'s, an understatement being what breaks a bound; and one above it is a cost's upper bound. A smaller figure because a description's releases fall on ticks is no more composed here than the catalog's §12 composes it in `/1`.
- **Which way each rounds.** What a sum lies within, a reach, a horizon, a modulus or a delivery bound, rounds down to the analysis's unit, where each cost rounds up, as §2's table says of each: at a unit of 1 µs, a horizon of 6553.5 µs is 6553 (`RA-H2`). A fact stated bare, absent or as a bound has no value, as the relation reads it.

### 2. Each alarm's interrupt is a declared source

Each requester that takes a channel for an alarm has a declared source of its own: an entry of the analysis's `Source`, with `C_s`, `T_s`, `J_s`, an acknowledge point and a priority. This is round 21's better decision, and the variant already says it: "Counter-wrap, timekeeping, overrun and watchdog interrupts … are sources like any other". So the recurrence, the ceilings and the admission conditions do not change, and what the sources' proofs rest on is what an alarm must then be shown to meet.

**One source per alarm, not per route.** Model §8 rule 8 reports one route for each provider and kind, and a device of two channels gives one route two alarms, whose arrivals can coincide: no one separation describes them, and a merged one could be zero, which condition 3 refuses. So `/2` writes one line per alarm, which rule 8 and the runtime plan's §2.5 and §2.9 say of each alarm where they speak of a route (`RA-H1`), and an alarm needs a line of its own, as a request of its own: `one-request-per-arrival` is owed of each, and `channels` counts those lines (§1).

**On a target an alarm also asks what §1's reasons ask**, the engine adding it, so an adapter's text does not change and neither does anything on the simulator, which has no idle and no wiring. `(alarm-wiring controller)` joins what is asked of the device it programs: of the requester that binds `relative-delay` or `absolute-deadline` on a device itself, and of an adapter instance's `beneath` where an instance programs it. It, `relative-delay` and `absolute-deadline` are facts of the function `counter`, so model §8 rule 13 binds them to one block. Rule 14 reads a fact of that function that is not consumed as a reader of a time base, and the kind allows `use consumed` only on a boolean fact or a group's head, so as it stands it would read an alarm's kind as one.
It says how a device raises and reads no time, as the wiring, `compare-step` and `compare-window` do, so `RA-H8` amends rule 14 to read none of them. That its device runs in idle and has a counter to read, `counter-modulus`, `tick-rate` and `observation-coherent`, since the code that writes a compare reads the time, what kind of alarm it is, what one write reaches, its compare's step and its window are asked of the device bound and of nothing else, by the joint rules (`RA-H1`): `available-in-state` as a requirement's qualifier is judged at everything the requester reaches (model §8 rule 13), which would refuse an alarm's service over its console. A device's kind is a level compare or a delay. An edge compare is refused, since "raised at the write and never lost" rests on a level, and an edge raises nothing until the count comes round.

**What each needs, and who owes it.** An alarm bound directly, `relative-delay` or `absolute-deadline` on a device with no instance between, reads as an expiry: it has no step of its own, and what stands ahead is what its requirement asks.

**The floor: `T_s` is enforced, not assumed.** A rate is no separation: "one arrival per deadline delivered" says how many, and the variant's `T_s` is how close. A job of period 100 arming one deadline per job can place two arrivals 50 apart, or 10, by which deadlines it picks and when it runs. Nor can an owner state the least one: the last segment of a chained delay can arrive just after the re-arm, a deadline due at its write arrives at that write, and each hangs on a response time. So the code that writes a compare holds it past the last arrival:

```text
compare := max(deadline, last_arrival + T_s)
```

each write, a job's and a service's, a segment of a chain and a wake's next point, `P` past the one before, among them. Two arrivals are then never closer than `T_s`, whatever a job programs, with no input from the application. What it costs is a deadline's lateness, which `delivery` holds. `T_s` is the realization's figure, judged at that value: too small and the load fails the analysis, too large and `delivery` fails. Choosing it is no search here.

**What the code can know.** `last_arrival` is no value any code holds at a write: an arrival happens when it happens, the read of the time is `λ` before the landing, and a compare standing may match in between. So the code bounds it from above, in a masked run, by what it read and what it wrote. A read is a whole tick of the counter, up to `ρ` behind the time. `what_it_read_and_wrote` in `crates/rt-analysis/tests/alarm_model/timeline.rs` is this protocol, and is what the sums are held of; these words say what it does:

- **In its own service**, the compare standing, if at or before the time it read, `r`, is spent now, having raised this service or stood when another's write raised it, and the last arrival is at most that value, or on a delay the bound below. What is due at `r` is delivered by this service. Any other write, a job's or another alarm's service's that calls this node, keeps to the next two, since a compare standing there raised no service of its.
- A compare standing that may match by `r + ρ + λ` is **left**, and the service it raises picks up what is pending. Rewriting it could put two arrivals closer than the floor.
- Otherwise it writes the earliest deadline pending, never before `r` and never past what one write reaches less one `ρ`, so that a deadline farther off is written in segments, floored and then rounded up to the compare's resolution, `v`, which still lies within that reach. After the landing, still masked and within `λ` of it, it reads the time again, `b`. A `v` at or before `b` arrives at its landing or at `v`, whichever is later, and by `b + ρ` either way, so nothing is left standing and the last arrival is at most `b + ρ`. A later `v` stands, and arrives at `v` on a level compare, the two lying on one grid. With nothing pending it disarms the compare, or where it cannot, stands a value within the window below, whose arrival is paid for as any. A landing is one instant here: a device whose compare takes several stores disarms it first, so nothing matches between them (`RA-H6`).
- A delay-only device is programmed a count, `v − r` on its resolution, from the read and never early, and lands late by its own lag, so its arrival is at most `r + count + λ + ρ`, which is the bound the code holds. It knows the count it wrote, so what rounding added to it is not added again.
- **Where the time base is the counter itself** each of these reads is modular, and each window is its own. A deadline stands ahead of a read within `R`, and past it beyond. A compare standing stands ahead within `max(R, T_s + λ + ρ) + ρ`. The floor stands ahead only within `T_s + λ + ρ`, and beyond that it is past and holds nothing back: an alarm may idle for wraps, and judged within `R` an arrival long gone would hold a deadline back by up to `R`. An arrival a whole wrap gone that reads as recent holds one back within that window, which `delivery` pays and `write` holds.

The model reads each time as a whole tick, its times falling on its unit, where a step of `res` lies at most `res − 1` behind, and draws the read after the landing within `λ`, and a read farther than that breaks `delivery`, which is why `λ` covers it. A floor read off the value last written, the first thing one would write, does not hold: arrivals 4 apart against a floor of 17, and a response of 104 against a bound of 63. That set is outside the protocol's conditions, and inside them it still breaks: arrivals 36 apart against a floor of 40, where the protocol holds that set 40 apart.

**This is held by a model, and not by reading.** `crates/rt-analysis/tests/alarm_model.rs` runs the variant's timeline, unit by unit, and `compose` and `analyze` as they stand: masked runs contiguous with their decided switch as `L` reads them, `δ`, `γ` and a compare's resolution, `W_wake`, several alarms, tasks an alarm releases, and a read apart from a landing. Over 1,400 timelines of seeded random sets, each job programming as it likes, from past due to two periods ahead: arrivals are never closer than the floor, none is lost, no response passes the analysis's bound and no deadline passes `delivery`. With the floor off, the review's chain holds at a bound of 2,406 and misses on the timeline at 2,989, arrivals 10 apart. A timeline is no realization, and has no initialisation and no modular hardware of its own.

**Condition 5's paid-for rule binds it**: a trap taken runs one service, paid for by an arrival, whose one claim takes a request. So on a device wired to the core an alarm is refused by the search. On the simulator its trap claims the request (`RA-H3`).

**What the composition gains.** The record's roles allow a device's registers only to the service of its own source, so a node programming its alarm from a job has no role today, and that fact gates every composite. It gains one: a node that takes a channel programs that channel's compare, and any node bound to that device reads its counter, from a job inside its own masked run or from a service that calls it, initialisation disarming any other than a wake's or writing its placeholder as `RA-H6` says, and that alarm's service alone claims and completes it. Rule 14 binds every other requester of a deadline to that device, a `time.monotonic` that takes no channel among them, and rule 4 makes a source's handler a user, so a node is called from a route's service that is not its own.
A wake is first armed at the port's transition to run time, the last masked step before the first enabling of interrupts, for a value `P` past what it reads, which one write must reach (`RA-H2`) and that step's own length must not pass: an arrival during initialisation would wait out a masked run `L` does not hold, and no source arrives before that enabling (the composite-inputs record's §2). The runtime plan's §2.7 calls programming an alarm work for run time, which holds of `/1`, whose emitter generates no such call, and `/2` amends it for a wake, since nothing else would ever arm one, and for a compare that cannot be disarmed, whose placeholder is written there (`RA-H1`, `RA-H6`). Its `service.<source>` is anchored by the realization and not by a catalog record (`RA-H5`). What else in the record's §1 to §3 this touches is for `RA-H5` to say when it builds them.

**What the variant's `Source` cannot state** is what the alarm was for. So the scheduling checker holds what this table writes, once `J_s` is known (`RA-H2`). `alarm_model.rs` reads this table and runs its cells, so a sum here is the sum it holds, and a change here is a change there (`the_record_s_sums_read_as_they_are_written`).

- **`delivery`** runs from the programmed time, or the write if later, and `J_s` from the compare matching. What lies between them adds: the code's bound on the last arrival stands up to `λ + ρ` past it, the floor stands `T_s` past that, the value is then rounded up, by `ρ`, and a delay lands late by `λ + ρ` again. A deadline that came due before a service's read is delivered by that service, so it waits on nothing more. A deadline already due when written (`ROADMAP.md` §6.2) is raised at the write and never lost, the floor apart, so long as `room` holds. The model holds this sum over its sweeps, at resolutions to 16.
- **`update`** runs from one read of the counter in a service to the next, since an epoch is correct only while it is read once in every wrap. A service's read is at or past the point it was raised for, so the next point is at most `P` past that read. On a compare the code's bound is within `ρ` of that read, since a wake's service reads the compare that raised it and no arrival a wrap gone is among what it reads, so the floor is at most `T_s + ρ` past it, and a write landing with nothing left to wait for arrives within `λ` of it. On a delay the bound stands up to `λ + ρ` past the arrival, and the next count lands `λ + ρ` late, rounded up by `ρ`. `P` is what the service programs, and not the greatest separation of arrivals, which hangs on `J_s` and which no owner could state.
- **`room`**: what stands ahead and what is read past must lie within one modulus. A compare stands at most `max(R, T_s + λ + ρ) + ρ` past a read, and a deadline is read past by as much as `delivery` lets it wait and by how long its writer took, `W`, since a job preempted before its write writes a deadline already past. A deadline before its writer's own release has no such bound, and nothing a realization can tell of a raw value, so an application on such a time base states that its deadlines stand at or after their writer's release and within `R` (`RA-H7`). `R` is a deadline's and not a chain's segment, since a chain's deadline stands as far ahead as it was asked to. The search can only say that what is asked lies within the provider's `unambiguous-horizon`, which is `supported-horizon`'s offer (the adapters record's §2); only this knows how far a deadline is read past, so this is the rest of it. A time base with an epoch of its own has no such limit on what it reads, and what it writes has `window`. It can refuse what would hold: a wake's `delivery` is counted though nothing reads its point past, and a lower floor is the way out. The model's case is this, on modular arithmetic: the timeline has no modular hardware.

### 3. The order

An alarm's rank goes by the deadline it has to meet, ascending, among the sources:

- a source's: its stated `min-arrival-separation`, the no-loss limit of a source acknowledged at entry, as today;
- an `expiry`'s, or an alarm bound directly: the `delivery-bound` its requirement asks, and one asking none goes last, with what states no value;
- a `wake`'s: its provider's `unambiguous-horizon`.

It is deadline-monotonic over what a description or its provider states. ⚠️ It is a choice of order and no claim of optimality: the scheduling checker judges whatever the plan orders, and the Audsley search `RTP-H4` asks for stays `M2.21.2`'s.

### 4. A node's call cost

A job's call into a node's generated code is a call of a primitive. The composition's parts already say all it needs: `api.p` is "one call, from its first instruction to its last", `masked.p` "the longest contiguous masked stretch inside one call", and `n_{i,p}` the most one job makes. - **A span.** A node's call cost is a span, so it holds what the node calls in turn. ### 5. How a job receives an alarm

**A job receives an alarm only as a release: a task is released by it.** No context runs a job's code in an interrupt, and the variant's "Work a service defers runs as a declared task". So what `/1` refuses, a task that would receive an interrupt's code, has one meaning, and it is the one any interrupt has:

- An alarm's service releases the tasks declared `released by` it, as a source's does, and only on an arrival that delivers a deadline or a wake's point. A chain's segment whose read finds no deadline due, and a placeholder, deliver nothing, so each re-arms and releases nothing, and a job never hears of an expiry before its programmed time (`a_chain_s_segment_re_arms_and_releases_nothing`). The condition is the variant's: a task released on every such arrival has `T_i ≤ T_s`, since those arrivals are no closer than the floor. So the analysis is told it is released on every arrival, the variant's other reading, on some only, having no check of that at all (`RA-H4`). Two deadlines one arrival delivers release one job.
- **Something else programs it.** A task released only by an alarm it alone programs has no first job, and the analysis would hold of a task that never runs. So a first job is read off the graph of who can program what, by model §8 rule 4's users, from the assignment and the triggers, a least fixed point: the timer, a source and a wake's first arm, which the port's transition writes, give one, and an alarm gives one only where a job or a service that has one programs it. A set of tasks that program only each other's alarms has none, by two tasks or by more, nor has a task released by an alarm nothing programs, nor one whose alarm only such an alarm's service programs. A task with none is refused (`RA-H4`). "Can" is all a plan can say: a programmer that reaches the node and never arms it passes, which nothing short of running it could tell.
- **`/1`'s refusal stands until it can be said.** A task requester bound to an alarm directly, or to an `expiry` instance, is still refused. What a task released by an alarm lacks is a way to write the release: a trigger naming the alarm, as `(source X every)` names a source, which `M1.44` owes every sporadic task's source. The separation it reads is the alarm's floor. A task that binds one itself stays refused, with a trigger or without: by the first-job rule where it alone programs it, and otherwise since a job programs an alarm through a node it calls, the role's. That is `RA-H4`'s, and the refusal's repair then says so.
- **The system's own level has no such meaning, and stays refused.** It has no job, and runs nothing after initialisation, which runs masked and never waits on an interrupt (the runtime plan's §2.7). So a requirement for an alarm or an expiry at the system's own level has nothing to receive it. The repair is to move it to a service, or until `RA-H4` to a task's service.

## Why

- **One rule for everything that asks.** A release timer with rules of its own would be a second account of channels, device choice and refusal, each to be kept in step. The kernel asking as anything else asks needs one requester in the joint rules and no new judgement of channels.
- **Reuse a proof rather than amend one.** The variant's source term has been reviewed, fixture by fixture, against the failure this design would otherwise have to rule out again. What it needs in return is honest inputs, and §2 says where each comes from.
- **A deadline, since that is what an alarm has.** A source's rank by separation is deadline-monotonic where its deadline is its no-loss limit, so one key covers both.

**Alternatives weighed.**

- **The target's tick-rate block**, R3-1's. A counter may raise no interrupt, which is why this reads `relative-delay`, and it would ignore channels: R3-3.
- **Release by a named device in the target's file.** A target saying "this one releases" is a fact the target's agreement cannot check, and a target's file holds what its agreement checks (`decision_target-platform-description.md`).
- **`LONGEST` for the horizon.** It holds, and refuses a 16-bit counter at 1 MHz for periods of 1 ms and 1 s, which works.
- **One source per route.** Model §8 rule 8's key, and no one `T_s`, rank or bound describes two alarms on it.
- **`T_s` stated by whoever programs an alarm.** The first two rounds' answer. The owner cannot state it: it hangs on response times and on a chain's last segment, and round 2's reader built a set that holds at the stated figure and misses. A floor makes it what the code does.
- **A release timer bound and never due, with no timer-released task.** Round 2's answer. A modular compare's largest value comes round within a wrap, and its trap finds no release due. So `(timer none)` stands, and the variant owes it a reading.
- **A wake as a timer event of the release timer.** §2.
- **Timer routes last, as `/1` has them.** An expiry due soon could wait behind every slow source, past its delivery bound, though what ranks it is stated.
- **A term of its own for a multiplexer's overhead.** It runs inside a call or a service, each already charged whole.
- **A node's cost per callee, added up by the composition.** It would need the call graph inside the realization, which a description never states, and a span is what the parts already mean.
- **A job's code run in the interrupt.** It is what §5 rules out, and it would take condition 5's "Work a service defers runs as a declared task" with it.
