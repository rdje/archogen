# This repository's work never endangers the host it shares

- **Type:** `decision`
- **Date:** `2026-11-05`
- **Status:** `active` — by the director's instruction, "that's critical"; written by leaf `PROGRAM.127`, under review in `docs/reviews/decision_host-guard-reviews.md`
- **External sources:** none: it reads macOS's own figures, each named below
- **Owner / source:** leaf `PROGRAM.127` (`docs/tasks/PROGRAM.md`), the director's words of `2026-11-05`: the machine is shared with many other projects, it holds 24 GB, RAM use above 88% is the danger zone, and above 90% the host might crash.

## The fact / decision

**In plain words.** A job from this repository must never be why the machine falls over, and nobody should have to notice for it to stop. So a watcher reads the host every second, and stops this repository's own jobs well before the director's lines. Nothing heavy starts when the machine is already full; it waits. Another project's process is never touched, even when it is the cause: this guard can only take its own share out of the way. It guards against accident. It is no sandbox, and an agent set on going round it can.

**What it reads, on macOS** (`scripts/host_guard.py`, `read_memory`):
- RAM used: app memory, wired and compressed, as Activity Monitor adds them from `vm_stat`, or the kernel's `kern.memorystatus_level` if that is higher. File cache is not use: macOS gives it back. Measured against the director's own reading on `2026-11-05`: 85.6% here, 85% there.
- Memory pressure: `kern.memorystatus_vm_pressure_level`, 1 normal, 2 warning, 4 critical. macOS's own judgement, since the compressor can hold the percentage still while swap climbs.
- Swap: `vm.swapusage`. Disk: free space where this repository writes, and on the boot volume, where the host swaps.
- Each process's **footprint**, `proc_pid_rusage`, which counts what is compressed and swapped. RSS does not: on `2026-11-05` swap held 62 GiB while the largest process showed 0.9 GiB.

**Its lines** (`Limits`, in one place; an override may only tighten one, so no flag can loosen the guard. How much a fall is and over how long, what counts as writing and how far back growth is counted stand beside them as constants, which no flag reaches and `HOST-GUARD` holds as it holds the lines):

| When | What happens |
| --- | --- |
| RAM over 70%, pressure at warning, swap over 16 GiB, or a disk under its floor | no heavy job starts; `run --wait` waits for room |
| RAM at 85%, pressure at warning, or swap grown 3 GiB within a quarter of an hour while ours runs | our largest job stops, if it holds a quarter of a GiB or more |
| RAM at 88%, or pressure critical | every job of ours holding a quarter of a GiB or more stops, and every build |
| a disk under its floor (100 GiB here, 30 GiB on the boot volume), or 50 GiB lost on the volume within a quarter of an hour while ours runs, whoever wrote it | every job of ours that is writing stops, and every build. If none shows writing and the volume that is short has lost a GiB within ten seconds, a job that has started something new since the last sample |
| ours over 6 GiB | the largest job stops, one each sample |
| one process over 3 GiB | its job stops |
| over 512 processes | the jobs with the most stop, until it is under |

Each line judges alone and they add up, so that none can silence another: a disk's reason once switched the RAM line off. A whole `make focused` measured 0.77 GiB of ours on `2026-11-05`, on a third of the cores at lower priority, so the ceilings leave room to work.

**What is ours.** A process that shows it itself: its working directory or its executable is under the repository, or a process that shows so started it, wherever it then runs. A process merely mentioning the path is not ours: another project's build is not made ours by an argument. What a `run` of this root started is ours wherever it runs, since the `run` says whose it is. Spelt as the volume spells it, since this volume ignores case and the kernel's answer does not.

**A job is what is judged and what is stopped.** A job is the topmost process of ours with all of ours it started: what a person would start again. A compiler stopped under a script would only be followed by the next, and `verify` runs every step whatever the last did, so a line ends the job and its `run` says why. All of it goes, short of what is protected, an agent, a terminal, a `run` under it, the guard's self-test and what runs from the system's own places, such as `caffeinate`: a small `git` too, which is asked first and takes its lock away when asked, if it gets to run: what is still there a second later is stopped outright, which under pressure may be all it gets. A `run` is a job of its own, so the `make` or script that called it is another: a line stops the job, and whatever called it hears 143 and decides for itself. `make` stops; a script that goes on finds its next `run` held to the start line and judged like the last.

**What is stopped goes by what a job holds or writes, not by what it is called.** Under a quarter of a GiB, stopping it would not help the host, so at a host's line it is left alone, whatever it is: a `git`, an `rm` freeing disk, an editor with unsaved work, a tool server, a read, as long as it has started no build. A job holds what its processes hold together, so many small ones under one shell count as one. Small jobs apart hold only their own, and are the ceilings' to hold. A build is the exception, since it spawns more for as long as it lives. What only asks or cleans is no build, `cargo clean` among it, which is how disk is freed; nor is a `make` still waiting its turn in its `run`. At a disk floor it goes by what each job has written to the disk since the last sample, all of its life where it is newly ours, so a process that wrote before it came here and writes nothing now can be stopped at a floor, so a small `cat` feeding on its own output is stopped, and an `rm` or a script of them is not. A watcher's first sample has no last, so it counts nothing written.

**What is never stopped, nor counted.** An agent, found by searching its name, its executable and what an interpreter runs; a terminal, by name, by a login shell's dash, or a shell told neither a command nor a script; what runs from `/Applications/`, `/System/`, `/usr/libexec/` or `/usr/sbin/`, the system's own interpreters among it; the guard and its self-test, by a file named `host_guard.py` or `selftest_host_guard.py` given first to the interpreter or by this checkout's own path, a `run` of the self-test being a job for what `check` and `status` say. None of them vouches for what it starts: a build a terminal here runs elsewhere stays that project's.

**Never by a program's name across the host.** Stopping the incident that way killed another project's build, so the hook refuses `pkill` and `killall`, and `kill` of what a search of the process table found, `pgrep`, `ps`, `lsof -c` or `top`, unless that search's pipeline names this repository's path, and it reads each through the guard's own `run` and through `env -`. What is ours is stopped by its pid, and `kill` of numbers, `kill "$(cat job.pid)"`, `pkill -P` and `kill "$(pgrep -P 123)"` pass. `kill` of every process this user may signal, `kill -9 -1`, is refused, however the number is spelt and whatever signal it sends, `-0` sending none and `kill -1` alone naming no target; and so is `kill` of a table searched by anything but a pid alone, `ps -U 501` among it and `ps -ef -p 1`, which prints the whole table. A word `ps` takes as a pid, `ps "$PID"`, is taken as one, so a search spelt to look like that is a way round this, as any is.

**How nothing goes around it by accident.**
- `make` runs everything that compiles or tests through `scripts/host_guard.py run`, for any agent or person, and waits for room by itself. `run` is one job at a time: it waits its turn behind a build or another `run` of ours, by what the process table shows, so that no environment can claim to be its job and no removed file can give away its turn. It says what it is waiting for, says why its own job was stopped, and gives a job's status as a shell does. The job has a session of its own, so all of it can be stopped with no table to read, and it is ended if no watcher can read the host.
- `.claude/settings.json` checks every shell command first, a subagent's and `Monitor`'s too (`hook`). It reads a command by the shell's own grammar (`ShellReader`), not by a pattern over its text: what a substitution, a subshell, a `bash -c`, a `trap`, a wrapper or a here-document fed to a shell would run is read, and what a message, a comment, a quoted here-document, a case's pattern, an array, a `[[ ]]` or arithmetic only says is not. It refuses three things: input it cannot read, stopping by a name or all at once, and a command recognised as heavy at the start line, beside a build or a `run` of ours, or when no watcher has read the host lately, each told what to do. What the guard stopped is told beside the next command's result (the harness's `additionalContext`), to each agent for itself, a subagent apart from what started it by its `agent_id`, the last five and how many came before them, and refuses nothing, since the way out may be that very command. Everything else runs, whatever the host's state: a light command cannot hurt, the watcher holds what turns out otherwise, and a host in trouble must stay readable and repairable.
- Each command the hook lets through and each `run` starts the watcher if it is not running, which then sees everything of ours however it was started; `check` only reads. A guard changed under a running watcher holds from then: the watcher takes up the file as it stands, whatever it is doing, a line that raises among it, says that it did, and nothing goes unwatched between. It forgets what it had counted, so growth's quarter of an hour starts again from a taking up. One that can be seen to be broken, that does not compile or does not end as it ends, is not taken up: the watcher goes on as it was and says so, and a repair is a save. ⚠️ A second save, broken, in the instant between that look and the new image's own read ends the watcher with nothing said, as below: the look and the read are two, and nothing there is left running to say it. A watcher whose look refuses a newer file, as one from before `prove` came out refused any file without that verb, cannot take it up, since it is that look that would have to differ: it goes on as it was, and `status` says so. `stop` it, and the next command starts one from the file.
  One that compiles and fails when it runs, a half-done rename, fails where that name is read. In the watcher's start, or in what its loop does outside its round, it ends it, and no next command starts one that lives; in its round it goes blind; anywhere else it reads on, and what reads that name raises. Where the hook still passes, it and `run` read the host for themselves, so a job may start: a heavy command is refused once the watcher has not read the host for a minute, and a job under `run` is ended a minute after that, some two minutes on. Light commands run, as ever.
  At a commit `HOST-GUARD` holds what is staged, of everything it reads, the `Makefile` and the settings among it, and what the index no longer holds is gone: that the file compiles, ends as it ends and binds every plain name it reads, and, where the commit changes it, its self-test or this check, that a whole self-test passed on those very bytes, by the stamp that run leaves. A case by name, a copy, or a run that ended on other bytes than it began on leaves no stamp; one saved and put back during a run is not seen. The check itself runs from the tree, since something must, so one emptied there asks nothing of what is staged, and an unstaged edit of it is what it holds an unrelated commit to. An attribute or a keyword half renamed is the self-test's to find, where it runs that line, and nothing else reads it. A merge, a cherry-pick, a revert or a rebase runs no pre-commit, and in CI nothing is staged, so none holds the stamp: this repository lands by commits on `main`, the director merging a batch that has passed them.
  A line of a watcher's round that goes wrong, its code or a read, silences that round, each line of which it may have been about to judge: it is said as `unread`, in the log and by `status`, the watcher goes on trying at its slowest, staying for a job it last saw up to twice as long as it would stay idle, and it reads as blind, with what follows from that as above. Nothing tells a light command. A watcher that ends by an error before its round begins says so, as far as that file can. Its root is named as resolved, since it leaves the directory a relative spelling was relative to, and its `PATH` holds the system's, since it outlives what started it.
  The hook is the same file. What raises is refused by `onFailure` until it is repaired; what runs and does nothing, a file emptied or cut short, lets commands through and starts no watcher meanwhile: one already running stands until it is idle, `make` refuses, and a commit refuses only to commit such a file, reading what is staged and not what stands. `make` looks at the file's last line before any recipe, running nothing, so a guard emptied or cut short is a refusal and not a recipe read as passed. One broken so as to raise exits with its error. One that runs and does nothing some other way, an exit at its top, is no accident this looks for. It survives its own trouble, `cargo clean` or a full disk among it, and stays while anything of ours runs. A root that is gone ends its watcher, and nothing brings it back; one remade at that name is another's. A watcher that cannot read the host is said to be blind rather than taken for one that can, a process table that does not hold its reader among the causes. It reads every two seconds with nothing of ours running and RAM under the start line, every second otherwise, and every half second near the lines or under a disk's floor, since it costs the shared host too. `check` and `status` say what `run` would, but for a moment of up to five seconds beside a `run` waiting its turn, which they do not look for: one heavy job at a time beside the host's own room. The hook also refuses a heavy command beside a blind watcher, which `status` says as blind.
- `HOST-GUARD` (`scripts/check_host_guard.sh`) holds the Makefile whole by its digest, so a commit changing any byte of it moves that digest in the check too, which asks the self-test: reading its text, and then asking `make`, were each passed by what `make` can be told, a target's own `SHELL`, `BASH_ENV`, a `PATH`, and asking it ran what it says at parse. A `GNUmakefile` or `makefile` beside it is refused, since `make` reads those first.
  It refuses a commit that takes the hook off, lets it fail open or narrows it, or moves a line past its mark, as `Limits()` and `tightened` give it when the file runs. It holds the wiring it names and the lines: a new recipe that runs a build behind a script is the watcher's to hold. That the guard stops what it should and nothing else is `scripts/selftest_host_guard.py`'s, which the `self-tests` step of `integration` runs, by `check_host_guard.sh --self-test`. On a host over the start line it waits for room, up to fifteen minutes in all, before the cases that would add to the load, and a case the host took away meanwhile goes again with room. What it still could not run it says as "not run" and exits 20. `run_self_tests.sh` carries that up as incomplete, and the `self-tests` step of `integration`, which no quarantine row names, fails the tier by that runner's rule that no step exempts itself by its exit code: a host full for that long turns the tier red, says so, and the way out is to run it again. On a host that is not macOS it exits 21, which the runner counts apart and never as passed, and allows this gate alone.
  Two of its cases hold the rules whole rather than by example: each `bash` here, the system's 3.2 and the first on the path, runs each of some two hundred and sixty forms against stubs, and the reader must name exactly what it ran; and every state of the host is judged against one set of jobs. Reading more than bash 3.2 runs is allowed in one place: a case's bare `)` inside a substitution, which that bash takes for the substitution's end, as its own bug, and later ones do not; and what only later ones have, `coproc` and `{fd}>`, is held on those.

## Why

- **Every second, not at the end.** The incident's first lesson: a job's notification says when it ended, never what it did to the host meanwhile.
- **Footprint, and the host as a whole.** The lines are about the machine, because that is what crashes, and the ceilings about us, because that is what we control.
- **Stop, then say.** The stop cannot wait for a person, and the result of the next command says it.
- **A job, not a process.** Round 5's reader ran a script around a build at the danger line: eleven stops in as many samples, the script still running, and each stop refusing the session's next command, the `kill` of that script among them. What a person starts is a job, so that is what ends.

**Alternatives weighed.**
- **A proof that a changed guard runs, before a watcher takes it up.** Three rounds' answer, `prove` by a walk of the names, its own loop run once, a proof beside the watcher. Five rounds running the main defect lay in it, and each proof left something unproved, so it came out: what a save can be seen to have broken is not taken up, and the rest is what `HOST-GUARD` holds at a commit and the self-test in `integration`.
- **A watcher that leaves when its file changes, the next command starting another.** Round 12's. The next command's hook could look before it left, and a bare job then ran unwatched for its whole life. Taking itself up leaves no such moment, only the instant of a second, broken save.
- **`ulimit` or a memory limit on each job.** macOS does not enforce a resident or address-space limit on a process.
- **Running each command through a wrapper only.** A command not wrapped would go unwatched. The watcher reads the process table, so it holds whatever was started.
- **Stopping whatever holds the most.** It would be another project's more often than ours, and that is not ours to stop.
- **A Rust tool in `xtask`.** It would have to compile before it could guard the compile.
- **`ri_logical_writes` for what a process has written.** Tried for round 6's slow writer, measured `2026-11-05`: it did not count writes at write time either, 0.3 MiB of 10 MiB at 1.2 MiB/s, and it read a large `rm -rf` as 12 MiB written in 0.84 s, where the figure used read nothing. It would stop the way out of a floor.
- **A fall of any size.** A shared volume's figure moves with other projects, by 324 MiB in a half second at the most measured `2026-11-05`, so a script of `rm` at a floor was stopped within seconds, in 9 runs of 9. A slower script of short writers now goes unstopped by this line, and the 50 GiB line and the floors' writers stay.
- **A pattern over a command's text.** Four rounds of answers kept finding both of its edges: a word in a message read as a command, a command in a subshell not read, a comment's apostrophe paired with a quote. The shell's grammar is small, and the shell is an oracle no code here wrote.
- **Refusing the next command until a stop is told.** It refused the way out. The harness can say it beside the command's result.

## How to apply

- **What to do about the reading, the director's word of `2026-11-06`:** "Regarding RAM, Just observe the trend, it shouldn't cross 90% and still increasing. don't stress out. If it's cross 90% and keep increasing, then you might say, well, I think we might have a situation here. other than that, just chill." So the trend is watched quietly, a percentage or another project's load is no news, and a reader's brief says the same. RAM over 90% and still rising is what is said. Waiting for room or being stopped by the guard is routine: the lines above stand as they are, doing that work, and moving one is the director's to rule on.
- Heavy work is `python3 scripts/host_guard.py run --wait SECONDS -- CMD`, or `make`. One at a time: a reader never overlaps `make focused`.
- `python3 scripts/host_guard.py status` says what it reads, who holds the most on the host, the peak, and what it has stopped.
- A reader's brief says to test a size limit with a sparse file refused unread, never by loading gigabytes.
- A commit's hooks can hold more than a quarter of a GiB, so at the stop line or pressure at warning the job a commit stands in goes with them. Nothing is lost, the index and the message staying as they were: measured `2026-11-05`, a hook's interpreter at 0.41 GiB beside another project's 12 GiB compiler. So on a full host a commit goes through `run` as well: `python3 scripts/host_guard.py run --wait 1500 -- git commit -F git_message_brief.txt`.
- On another harness only this one has the hook, and the watcher ends when the work has been idle: heavy work there goes through `run` or `make`, which keep it running, or runs `python3 scripts/host_guard.py ensure` before each job.
- ⚠️ **What it cannot do.**
  - It cannot make the host safe from other projects. On `2026-11-05` the reading passed 90% with ours at 1 GiB and another project's two compilers at 10 GiB each; the guard stopped ours and said who held it, and that was all it could do.
  - It is no sandbox. It keeps accident out, and a command spelt to go round the hook, or a program of the same name earlier on the path, is not looked for. What runs here the watcher still holds.
  - A sudden jump can pass a line between two samples, and a job whose writers all begin and end between two shows no writing.
  - What a job has written is what has reached the disk, `ri_diskio_byteswritten`, and the file system holds some back. Measured `2026-11-05` over several runs: it reads nothing until some 8 to 15 MiB has gone, then moves in steps, so at a floor a slow writer is seen late, and how late varies: 1.2 MiB/s stopped between 6.7 and 13 s, and one at 0.6 MiB/s at 14 s where another went 20 s unseen. Writing through `mmap` reads as nothing written too: only the volume's own figures say either.
  - What escapes it: a process that detached itself and shows nothing here, and a command that first leaves the repository's directory, whose shell then shows nothing either. A session rooted in another project that comes here has that project's settings, so no hook; the watcher, if running, still holds what runs here. A shell fed its script on its input, `printf … | sh` or a here-document, shows as one told nothing, so as a terminal: spared, and what it starts is judged job by job, each stopped build followed by the next. Telling them apart would take a controlling terminal, and an agent's own persistent shell has none, so sparing is the cheaper mistake.
  - What it never stops it does not count: an application under `/Applications/`, such as Xcode's linker, can hold memory no limit sees.
  - A job that holds a quarter of a GiB or more is stopped at the danger line whatever it is, and at the stop line, 85% or pressure at warning, if it is our largest: an editor that large, a REPL, or an agent's tool server with its directory here. And a job goes whole: an editor whose `:!` runs a build at the danger line goes with it, unsaved words among what it held, and so does a tool server here whose helper writes at a disk's floor or starts a build there. It is asked first, given a second, and then stopped outright: what it does when asked is its own, as far as it gets. What holds less stays at a host's line, so small jobs apart are held by the ceilings, not the lines.
  - What it reads as ours by ancestry may surprise: a tool here that starts a build elsewhere makes that build ours. Growth counts what the host lost within the window while anything of ours ran, whoever caused it, so another project's writes or swapping can stop a job of ours, which may then be started again: nothing cheap can say who did it. A falling volume is read the same way: another project writing a GiB within ten seconds, under a floor, can stop a script of `rm` of ours, and 1.2 GiB has been measured. A job whose `run` is killed outright gives up its turn, unless it is a build, which is seen as one.
  - A worktree or submodule is its own root, with its own watcher, ceilings and turn, wherever it stands. One inside this checkout is under this root too, so this root's lines and turn hold it as well.
  - The hook's judgement of a heavy command is a courtesy to the host: what gets past it, a program in a variable, a script, a `find -exec`, a `python3` that allocates, the watcher still holds. `git commit` is not heavy to it, though a commit's hooks can compile. Nor does it read what a pipe feeds a shell, what a variable holds, a script's own lines, or what a shell given a `-c` is fed beside it.
  - `kill -0` stops nothing and passes, and `-P 1` is no parent to go by, however it is spelt: every orphan on the host has it.
  - A search of the table by any other program is not read, and what it finds and a `kill` of it pass: the same courtesy as the rest of this list. A kill of a number worked out by `$((…))` or `$[…]` is refused though it could be plain, which costs a rewrite.
  - What `ps` cannot read the words of, `(env)`, is no job until a look can, so at most one look late, but for a process that names itself so, `exec -a "(worker)"`, which stays no job. A wrapper the reader has no line for hides what it wraps, as a script does. A root's name that goes on with ` -`, or holds ` -- `, is not told apart on a flat command line.
  - `kill "$(…)"` is judged by that substitution alone, so what a search left in a file, a function or a variable that the substitution then prints is not followed: `pgrep -x x > pids; kill $(cat pids)`.
  - A search names this repository if any word of its pipeline does, but for what `grep -v` or `pgrep -v` excludes and where `tee` saves: a pattern naming this root can still say nothing of what it finds.
  - `kill` of a search it cannot follow is not seen: a variable set by an earlier command, or a search fed in after the loop that uses it (`done < <(pgrep x)`). A search before a `kill` of a variable is read as feeding it, so a `kill "$PID"` after an unrelated search by name is refused, with no harm but a rewrite.
  - An agent is found by a search of names, so a script that happens to be called `codex.py` is spared, though a directory named so among a program's arguments is not; a new agent with no such name is not spared. Wrongly sparing costs less than wrongly stopping.
  - It sees this user's processes alone, so "who holds the most" means of this user's.
  - A job has no controlling terminal, so one that prompts on the terminal fails. That is what a session of its own costs.
  - It reads macOS only: elsewhere a job runs unwatched, and says so.
