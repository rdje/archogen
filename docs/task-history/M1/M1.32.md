- ID: `M1.32`
  Status: `done`
  Goal: `archogen check` given a **kind module** says what it is instead of refusing it as an invalid
  description — the sibling of `M1.29.1` for the other file kind that is not a description.
  Reproduce / issue: found by `M1.31`'s census, which runs every tracked description through the command.
  ```text
  $ archogen check docs/semantics/kinds/os-rt.eadl ; echo $?
    error[schema-unknown-kind] … `defkind` is not a known kind …
    archogen: invalid-description: 1 diagnostic(s) in docs/semantics/kinds/os-rt.eadl        exit=10
  ```
  The file is the toolchain's own language definition, embedded in the binary by
  `crates/archogen-cli/src/check_cmd.rs`'s `KIND_MODULES`; `archogen check` reads it as a *description*
  and hands back a verdict about a system. An author extending the language (`ROADMAP.md` §5.6, `M6`)
  who checks their own `defkind` file meets the same false verdict.
  Acceptance: decide and state what `check` does with a kind module — refuse it as `unimplemented` naming
  the leaf that admits user kind modules, or validate it as a kind module with `shipped_registry`'s own
  reader — through the routing point `M1.29.1` introduced; both commands agree; RED arms; `make focused`
  exit `0`.
  Priority: **low** — no surface claims `check` reads a kind module, and the shipped ones are exercised
  by `shipped_registry` on every run.
  **Decided `2026-09-30`: refused as `unimplemented`, naming `M6.3`.** Validating the file standalone with the
  registry's reader would answer `0` for a kind module that redefines a shipped kind, because the clash only
  shows when the two are loaded together. That is an "ok" the tool cannot stand behind. `M6.3`, the first
  extension experiment ("a new eADL composite feature/kind … no parser or core-language edits"), is the leaf that
  has to load a kind a user writes, so it owns the answer. The routing is `frontend`, which both commands share.
  A file is a kind module when any declaration is a `(defkind …)`, by the rule `is_module_file` uses. A module
  file is recognized first, since the elaborator owns that file's malformations.
  **Closed `2026-09-30`.** Both commands answer a kind module `unimplemented`, exit `20`, naming where its first
  `(defkind …)` is and `M6.3`. They print no diagnostic and no verdict, and `build` creates no output directory.
  Exactly two tracked files moved in the verdict ratchet, the shipped kind modules; nothing else did.
  Verification: see the checklist.
