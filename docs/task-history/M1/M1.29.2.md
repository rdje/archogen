  Design, decided `2026-09-29` before any code and written into `docs/semantics/reference.md` §6 first:
  **(a)** an import of `a.b` is read from `a.b.eadl` in the **module path**, which is the directory holding
  the description the command was given — one directory, so no two candidates can compete and no search
  order has to be invented; a `--module-path` is deferred until a real layout needs one. **(b)** The file is
  found by the imported name and **verified** by its declared one — rule 4 stays firable, which is the
  reading of `M1.29`'s "resolved by declared name" that keeps `module-name-mismatch` a live rule (the ⛔
  constraint below). **(c)** A module name is dotted lowercase segments, because it becomes a file name: no
  separator may escape the module path and no two spellings may name one file on a case-insensitive
  filesystem and two on another; anything else is `module-bad-import`. **(d)** A module file that exists but
  cannot be read is a failure of the **invocation**, reported like an unreadable description (`usage`, exit
  2), not `module-not-found` — which would be a false statement about the description. **(e)** The root is
  the file the command was given and is never looked up, so its declared name is not compared with its file
  name. **(f)** After elaboration the command stops: diagnostics are `invalid-description`; a clean tree is
  `unimplemented` naming `M1.29.3`, because the model passes cannot read an elaborated program until the name
  rule exists. **(g)** Fixtures: one directory per case under a new conformance root
  `docs/semantics/modules/`, the root file carrying `case:` / `expect:` / `code:` / `why:`, imported files
  carrying no `expect:`.
  Goal: a disk-backed `ModuleSource` wired into `archogen check` and `archogen build` ahead of the schema
  pass, through the routing function `M1.29.1` lands — so a module file is **elaborated**, and every §6 code
  a module tree can produce is produced by a command.
  Acceptance: the naming rule — how an import's module name becomes a file, and where the module path
  comes from — stated in `docs/semantics/reference.md` §6 **before** it is implemented, with the reason;
  both commands elaborate through one function so they cannot disagree about a module tree; each of §6's
  24 `module-*` codes reached through `archogen` from a tracked fixture, or recorded as a stated limit with
  the reason (`module-too-large` fires only on a source of 2^32 bytes, which is **F-H**'s row); an
  elaborated tree that has no name rule yet to be type-checked with is refused as `unimplemented` naming
  `M1.29.3`, never checked with unresolved names; `docs/book/src/modules.md` shows transcripts rendered by
  the command; RED arms; `make focused` exit `0`.
  ⛔ **Design constraint found while decomposing, recorded so `.2` does not rediscover it.** `M1.29`'s
  acceptance asks for a module path "resolved by **declared name** and not by filename". Read literally —
  index every file in the module path by the name its `defmodule` declares — that makes §6 rule 4's
  "a module whose declared name is not the name it was imported by is refused" **unfirable**, and
  `module-name-mismatch` a row that reads like a live rule and can never fire, which is exactly what §4
  rule 4 calls a rotted row. Rule 4 presupposes that the name an import looks up and the name a file
  declares are two things that can disagree. So `.2` resolves the file by a **stated** rule from the
  imported name and keeps the declared name **authoritative** — a file that declares another name is
  refused, never trusted — and records that reading of the acceptance on the leaf.
  ⛔ **Second constraint: a tracked module fixture is a manifest decision.** `docs/semantics/conformance.md`
  rule 4 puts every tracked `.eadl` in the repository into the `eadl/1` conformance suite or requires it to
  be excluded, and every suite member's canonical form is a frozen construct in `BASELINE.txt`. So the
  fixtures `.2` needs are declared under a root whose purpose is stated in the manifest's `suite-roots`
  table, each carrying the verdict header the suite reads, and the baseline movement is covered by a
  migration note — which is why `M1.29.1` writes its one module file into `CARGO_TARGET_TMPDIR` instead.
  Priority: **high** — `M1.29`'s capability half.
