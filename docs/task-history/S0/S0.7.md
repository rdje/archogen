- ID: `S0.7`
  Status: `done`
  Goal: fix the one test in the S0 suite that fails on a **cold** run — it writes a source file
  directly into `CARGO_TARGET_TMPDIR` without creating it, and cargo creates that directory when it
  *builds* a test binary, not when it runs one.
  Reproduce / issue: surfaced by `PROGRAM.19`'s artifact cleanup, which removed `target/tmp` (test
  scratch). With the test binaries cached, `cargo test --all` then fails exactly one test, and only on
  that first run: `a_description_with_no_system_says_there_is_nothing_to_build` panics at
  `crates/archogen-cli/tests/s0_build.rs:211` on `.expect("writable")`, giving
  `test result: FAILED. 6 passed; 1 failed`; the immediately following warm run reports
  `36 suites, 421 passed, 0 failed`. Deterministic, and reproduced twice deliberately:
  `rm -rf target/tmp && cargo test --all` → the same single failure each time.
  Impact: a suite that is green only because a previous run left a directory behind. Anyone who cleans
  `target/tmp`, and any CI runner pairing a cached build with fresh scratch, sees a failure no change
  caused — and the failing test's *name* is about description validity, which sends the reader to the
  wrong place entirely.
  Acceptance: the cold run passes; every other `CARGO_TARGET_TMPDIR` site is censused rather than
  assumed safe; the fix says why the directory has to be created; the focused tier is green; F28's own
  gate still passes.
  Verification: see the acceptance checklist below.
  Commit: `ARCHOGEN-S0-0059 (leaf S0.7)`
  promotion: declined (the durable content now lives where the next reader meets it — the comment above
  the `create_dir_all` call in `s0_build.rs` states cargo's build-time behaviour, and this leaf records
  the census showing it was the only affected site. A knowledge card would be a third copy of a fact
  stated in the code it concerns, and the adjacent principle is already retrievable as
  `docs/knowledge/a-gate-is-only-as-sharp-as-its-fixtures.md`.)
