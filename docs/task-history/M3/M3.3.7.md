    can — and whether this profile's engine can is `M4.1`'s to say, `unsupported-profile` there if it cannot.
  - **Nodes** (D2, R6): the providers an assignment binds for the requesters a system serves, closed over bindings — an
    adapter or record bound for a served requester is served, and its own bindings count (`M3.2`, `M3.7`, told in their
    leaves) — and the services and policies the system serves, each marked with its kind. The system's own level, which
    initialises nothing, and its tasks, which start after all initialisation (the schedule's), are no nodes.
  - **Edges, each with its reason** (D1, D4, R7): provider to requester for each binding — the requester may call it
    while it initialises, the conservative reading — except between a provider and one it composes, at any depth, as
    `composes` reads it, and a provider meeting its own requirement; used to user for each `uses` or `needs` by which a
    served service or policy names another, read by `named_by`, the one reader of `SR-H15`'s edges `System::read` uses.
    Hardware naming hardware — a platform's `uses` or `needs` of a block — is composition, no edge.
  - **What it reports** (D4, D5, R8): its own entry, `Joint::initialization(&System, &[Binding])`, so no earlier test
    moves; the graph — nodes and edges sorted by name, each edge with its binding's requirement span or its naming —

    this rule's.

    context is `M3.3.8`'s; what initialising a node does is the engine's. A component made of `uses` alone has no
    provider, so it never reaches `SR-H18`'s code.
